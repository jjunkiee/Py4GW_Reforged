# Refactor Sequencing

Status: proposed
Scope: staging and verification order for the planned bottom-to-top refactor of
`Py4GWCoreLib` and the consumer tier
Authority: [refactor-baseline/](../refactor-baseline/README.md) for structure;
`graph.json` and `boot_closure.py` for every number; current source for every verdict

The [refactor baseline](../refactor-baseline/README.md) answers *what each component is and
who owns it*, and stops deliberately before sequencing. This document is that missing half:
**in what order the work happens, what proves each step, and what must not be touched.** It
proposes no new verdicts. Where it names a component's disposition, the
[component register](../refactor-baseline/component-register.md) is the authority and this
document is the schedule.

The strategy is a deliberate demolition: reduce the repository to the smallest thing that
still boots through the launcher, refactor that core while nothing depends on it, then
re-admit functionality one layer at a time with a working client at every step.

## The two truncations

The repository has two independent sizes, and only one of them responds to deleting files.
Conflating them is the main way this refactor can waste a month.

| Measure | Modules | Lines |
|---|---|---|
| Whole repository, in scope | 1,701 | 659,975 |
| Static closure of the widget host (all import statements) | 477 | 183,044 |
| **Boot closure** - what actually loads when the DLL runs the host | **272** | **133,710** |
| Consumer tier - `Widgets` + `Sources` + `Bots` + `Examples and tests` | 1,076 | 441,163 |

Generated by `boot_closure.py` from `graph.json` at `8dfdcaf2`; see
[The measurement workflow](#the-measurement-workflow).

The **boot closure** is this plan's central metric and it is new here - the baseline does not
carry it. `graph.json` records every import statement, including the 1,141 that sit inside
function bodies and never execute at load. Counting those overstates the startup surface by
about 40%. The boot closure counts only imports reachable at module load.

Two consequences follow, and they define the whole plan:

- **67% of the repository is already outside the boot path.** Deleting the entire consumer
  tier - 441,163 lines - changes what loads at startup almost not at all. It is still worth
  doing, because it clears the room, but it is not where the coupling lives.
- **The core loads 133,710 lines to draw a launchpad.** That number does not fall by deleting
  anything. It falls by cutting import edges. This is the actual refactor.

So: **Truncation A** deletes the consumer tier and is cheap, safe and enormous.
**Truncation B** shrinks the boot floor and is the real work. Phase 2 does B before Phase 3
does A, for reasons given below.

### Why the boot floor is what it is

The dominant cause is one import.
[`WidgetManager.py:17`](../../../Py4GWCoreLib/py4gwcorelib_src/WidgetManager.py#L17) does:

```python
from Py4GWCoreLib.GlobalCache import GLOBAL_CACHE
```

[`GlobalCache/__init__.py`](../../../Py4GWCoreLib/GlobalCache/__init__.py) constructs the
singleton at module scope (`GLOBAL_CACHE = GlobalCache()`), which builds the camera, effect,
item, inventory, merchant, party, quest, skill and skillbar caches plus shared memory - which
reaches `HeroAI/settings` to `HeroAI/commands` to `BuildMgr` and 73 build-content modules.

The widget manager uses `GLOBAL_CACHE` for exactly one thing: `.ShMem`, to disable widgets on
other accounts and read HeroAI options (`:792`, `:796`, `:1154`, `:1158`, plus a
function-level use at `:1209`). **Eighty-nine thousand lines to obtain a shared-memory
handle.** Verified at source.

This is the same defect family the register records as `Improve in place` on
[`Py4GWCoreLib/__init__.py`](../../../Py4GWCoreLib/__init__.py) - the 323-module facade cycle
- seen from the boot path rather than from the import graph.

## The measurement workflow

Two committed generators drive this plan. **Neither is optional and both run at every phase
boundary.** They are the difference between a refactor that is measurably progressing and one
that merely feels like it is.

### 1. The dependency graph

```
python docs/architecture/refactor-baseline/tools/build_graph.py
```

Rewrites [`graph.json`](../refactor-baseline/graph.json). Output is deterministic - every
collection is sorted before serialisation - so on an unchanged tree a rerun is byte-identical
and `git diff graph.json` is a real signal. This is the baseline's own tool and its contract
is described in [refactor-baseline/README.md](../refactor-baseline/README.md).

### 2. The boot closure

```
python docs/architecture/refactor-baseline/tools/boot_closure.py
```

Reads `graph.json`, re-parses each source file to separate module-level imports from deferred
ones, and reports:

- the boot closure size, in modules and lines;
- the boot closure broken down by namespace;
- the **severance edges** - every import from a retained area into the consumer tier, which is
  the Phase 3 gate;
- the **ranked cuts** - which single edge, if severed, releases the most modules from the boot
  closure, which is the Phase 2 work queue.

Also deterministic. It prints a summary by default and writes JSON with `--out`. Nothing is
committed by default; the report is cheap to regenerate and does not need to be a stored
artifact. Both tools pass Pyright in `strict` mode with zero errors (1.1.411) and import
nothing from this repository, so they run outside the injected client.

### The loop

Every phase below ends with the same three steps, and a phase is not finished until all three
are done:

1. Run `build_graph.py`, then `boot_closure.py`.
2. Record the boot-closure module and line count in the commit message.
3. Confirm the number moved in the direction the phase intended. **If it did not, the change
   did not do what you thought it did** - investigate before continuing.

That last step is the point of the whole workflow. A refactor of this size generates a
constant supply of changes that feel productive and alter nothing structural. The boot
closure is indifferent to how the work felt.

## Phase 0 - Preserve the map

You are about to destroy the tree these documents describe. Preserve the evidence first.

1. **Commit the baseline set.** The `refactor-baseline/` directory and its README/index edits
   are currently uncommitted. Commit them before any code changes. After Phase 3 the register
   cannot be regenerated - the components it describes will not exist.
2. **Tag the origin.** `git tag refactor-origin` on the current commit. Every "what did this
   look like before" question for the next several months resolves to this tag.
3. **Branch.** Work proceeds on a refactor branch. `main` stays shippable throughout.
4. **Snapshot user data outside the repository.** Copy `json/`, `Settings/`, and
   `Py4GW.ini` somewhere git does not manage. This is the one hazard deletion genuinely
   creates and it is covered under [Standing constraints](#standing-constraints).
5. **Establish the waypoint.** Run both generators and commit `graph.json`. This is the
   zero-point every later measurement is read against.
6. **Establish the test baseline.** Run the 18 offline tests and record which pass, then
   decide whether to fix the failures or accept them, because "did I break this?" is
   unanswerable in Phase 4 against a suite that was already red. **Done:** all 18 ran at
   `refactor-origin` giving **11 pass, 7 fail** - two more failures than the baseline
   recorded. Four harness defects and one production defect were repaired and the two
   condemned `test_sqlite3` files were left red on purpose, giving **16 pass, 2 fail** with
   both failures known. Diagnosis and per-test attribution are in
   [refactor-phase-0-waypoint.md](../records/refactor-phase-0-waypoint.md).

Exit criteria: baseline committed, tag exists, user data copied off-tree, phase-0 boot-closure
numbers recorded, offline pass/fail set recorded.

## Phase 1 - Define and prove the MVP gate

The MVP gate is one sentence, and everything downstream depends on it being narrow:

> The launcher starts `Gw.exe`, injects the DLL, the host bootstraps, and the launchpad
> renders - with zero widgets present.

That is testable by eye in under a minute and it proves the runtime is alive: process launch,
injection, Python host, settings resolution, ImGui draw path. The boot path is
[`Py4GW_widget_manager.py`](../../../Py4GW_widget_manager.py), whose three module-level imports
are `Settings`, `WidgetManager` and `launch_bar/launchpad`.

**Recommended: exclude the `Widgets/System` tier from the MVP.** It is force-enabled during
bootstrap - the host calls `_apply_ini_configuration()` at
[`Py4GW_widget_manager.py:63`](../../../Py4GW_widget_manager.py#L63), which overrides the saved
state for any `Widget:System` section at
[`WidgetManager.py:951`](../../../Py4GWCoreLib/py4gwcorelib_src/WidgetManager.py#L951) - and so
the tier looks mandatory. But
[`Messaging.py`](../../../Widgets/System/Messaging.py) is 4,172 lines holding the *receive*
half of the multibox command protocol while the send side and transport are both core. The
register's verdict on it is `Split`, for exactly that reason. Carrying it into the MVP carries
the misfiling through the entire refactor; it returns in Phase 5 after the dispatcher goes
home to its transport owner. This is a recommendation, not a finding - see
[Known Unknowns](#known-unknowns).

**Before Phase 2, confirm the boot closure against a live client.** Instrument the host to log
`sys.modules` after `_bootstrap_once()` and compare against the 272 modules
`boot_closure.py` reports. The tool measures static reachability at load time; it cannot see
native callbacks or path-loaded widgets. If the live set differs materially, the cut ranking
in Phase 2 is built on sand and must be re-derived before any effort is spent on it. This
check costs minutes and protects weeks.

Exit criteria: gate sentence agreed; live `sys.modules` capture compared against the static
boot closure; any discrepancy explained or the ranking re-derived.

## Phase 2 - Cut edges

**Cut before deleting.** The ordering is the single most important decision in this plan and
the temptation will be to reverse it, because deleting is more satisfying. Two reasons not to:

- The graph is the map. Deleting the consumer tier first destroys the fan-in evidence that
  tells you whether a core edge is safe to cut.
- Edge cuts are individually verifiable against a working client. Once 441k lines are gone,
  a regression has a much larger search space and no reference build to compare against.

Work the ranked cuts from `boot_closure.py`. As measured at `8dfdcaf2`:

| Cut | Releases |
|---|---|
| `WidgetManager.py:17` -> `Py4GWCoreLib.GlobalCache` | 180 modules / 89,091 lines |
| `Py4GWCoreLib/__init__.py:125` -> `Botting.py` | 37 modules / 8,582 lines |
| `routines_src/BehaviourTrees.py:64` -> `behaviourtrees_src/` | 22 modules / 18,024 lines |
| `Routines.py:13` -> `routines_src/Yield.py` | 10 modules / 3,583 lines |
| `Py4GWcorelib.py:14` -> `system_settings/recolor_beacons` | 7 modules / 1,485 lines |

The first is the demolition charge: take the `ShMem` handle directly, or better, inject it,
rather than importing a singleton that constructs nine caches to reach one field. Expect the
boot floor to fall from roughly 134k to roughly 45k lines before a single file is deleted.

Then sever the two module-level severance edges at
[`behaviourtrees_src/items.py:72-73`](../../../Py4GWCoreLib/routines_src/behaviourtrees_src/items.py#L72),
which are the only load-time imports from core into the consumer tier. These are PF-3's
severance, scoped by the graph rather than by estimate.

Finally, repoint the facade back-edges reachable from the host. The register's
`Improve in place` verdict on `Py4GWCoreLib/__init__.py` is this same work. The baseline
recommends rehearsing on cycles 4, 6 and 7 first - small `__init__` to submodule loops of
identical shape - and that advice holds: they are cheap, they are real, and they teach the
pattern before it is applied to a 323-module component.

Regenerate both reports after **each** cut, not at the end of the phase. A cut that does not
move the boot closure did not do what you thought.

Exit criteria: boot closure materially reduced and the reduction recorded per cut; MVP gate
still passes on a live client after every cut; zero module-level severance edges remain.

## Phase 3 - Amputate

Only now delete. The consumer tier is 1,076 modules and 441,163 lines - 67% of the repository
- and it is held to the core by **ten import statements**, which `boot_closure.py` lists
under severance edges. Four are module-level (two of them in the deletable root example
`Py4GW DEMO 2.0.py`); six are deferred, all reaching
`Sources/frenkeyLib/ItemHandling`, and each is recorded in the register's `frenkeyLib` rows.

The deferred six break the core only when the owning function runs - which is harder to notice
and no less real. Resolve them in Phase 2 or accept that identify, salvage and auto-inventory
are non-functional until Phase 5 returns them. Either is defensible; leaving it undecided is
not.

Delete: `Widgets/`, `Sources/`, `Bots/`, `Examples and tests/`. Retain:

- the 18 offline `test_*.py` files, which are the only real regression coverage in the
  repository - two production modules name a test as their offline proof, so the coupling runs
  both ways even though no production module imports them;
- `Py4GW_Reforged_Launcher/`, which has zero edges in either direction and is not in the way;
- `py4gw_bridge/`, the cleanest boundary in the repository and useful for driving the stripped
  client during Phases 4 and 5.

Also clear the 24 empty directory husks the dependency map lists, particularly root `HeroAI/`.
An empty directory that returns `True` from `.exists()` and silently disables a widget is
precisely the kind of thing that costs an afternoon three months from now.

Exit criteria: consumer tier removed; MVP gate passes; `build_graph.py` runs clean with zero
broken in-repo imports in the retained tree.

## Phase 4 - Refactor the naked core

You now hold roughly 206k lines of `Py4GWCoreLib` with no consumers watching. **This is the
only period in the project's life when a public contract can change without a blast radius**,
and it should be spent deliberately rather than on whatever is most annoying.

Work the register's non-`Keep` verdicts bottom-up, in dependency order:

| Order | Component | Register verdict |
|---|---|---|
| 1 | `native_src`, `enums_src` | `Keep` - already clean leaves; break the one small `native_src` cycle |
| 2 | `GlobalCache` | `Keep` - but the Phase 2 cut changes its construction contract; settle that here |
| 3 | `py4gwcorelib_src` | `Split` - 19 infrastructure modules against a 100-module `system_settings/` feature pile |
| 4 | `routines_src` | `Keep` - the owner is sound; it was the consumers that bypassed it |
| 5 | `HeroAI`, `Builds` | `Keep` / `Improve in place` - repoint the 524 `Builds` facade back-edges |
| 6 | `botting_src` | `Improve in place` - includes the broken `Widgets.Blessed` import |

The `Widgets.Blessed` break at
[`INTERACT_src.py:156`](../../../Py4GWCoreLib/botting_src/subclases_src/INTERACT_src.py#L156)
deserves specific attention here: it is the only static core-to-widget edge in the repository,
it is broken, and Phase 3 has just deleted the widget it was reaching for. Fixing it during
this phase is natural; leaving it means `Botting.Interact.GetBlessing()` stays silently dead.

Exit criteria: each verdict either executed or explicitly deferred with a reason; boot closure
recorded; offline tests pass; MVP gate passes.

## Phase 5 - Add back by layer

Re-admit in the conceptual model's own layer order, **one layer per commit**, with the
generators run at every boundary. A layer is done when the runtime proves it, not when it
imports.

| Layer | Re-admit | Done when |
|---|---|---|
| L4 | `ShMem` plus the `Messaging.py` dispatcher, returned to its transport owner | a multibox command round-trips between two clients |
| L3 | `GlobalCache` caches | state reads are correct on a live client |
| L6 | `routines_src` - `Yield`, behaviour trees | one bot completes one route end to end |
| L5 | `HeroAI` and `Builds` | combat runs on a hero |
| - | `system_settings` features, one per commit | each feature's previously saved settings still load |
| - | Widgets, one directory per commit | the catalog shows it, it enables, it draws |

Two rules govern re-admission, and they are what convert this from a rewrite into a refactor:

- **A component returns only on its register verdict.** `Keep` returns as-is. `Split` and
  `Fold` are performed *before* re-admission, not promised afterwards - a component re-admitted
  intact with a note to split it later will not be split later.
- **`Remove` verdicts never return.** The 10 `Remove` rows are already deleted by Phase 3, so
  the demolition executes them for free. Re-adding one is a decision, not an oversight to be
  corrected silently.

Re-admitting a widget requires restoring its `.widget` marker directory. Discovery is by
marker, not by import - see the reachability rule in
[refactor-baseline/README.md](../refactor-baseline/README.md#the-reachability-rule--read-before-acting-on-any-zero-fan-in-row)
- so a widget whose marker is missing is invisible rather than broken, with no error.

Exit criteria per layer: its runtime proof above; generators run; boot closure recorded;
offline tests pass.

## Standing constraints

These bind every phase.

**Saved user data is not in the import graph, and deletion is the one thing that genuinely
endangers it.** Code is recoverable from `refactor-origin`; a user profile that a re-admitted
component can no longer read is not. `WidgetCatalog` alone owns 13 `Settings` sites across
three INI files; `MerchantRules` is at `PROFILE_VERSION = 36` with five persisted contracts.
Moving code must not move keys. The register's blast-radius column records this per component
and is authoritative.

**Static conformance is not progress.** Inherited directly from the
[decision autopsy](../records/reforged-migration/frenkeylib-decision-autopsy.md): a clean
import, a passing type check and a shrinking boot closure prove that the code is *structurally*
better. They do not prove the client still plays the game. Every phase exit above requires a
live gate for that reason.

**Ownership analysis is not product retirement.** The autopsy exists because that line was
crossed once. This plan schedules the register's verdicts; it does not decide whether a
feature should exist. Where the register recorded `Unresolved - no verdict` - `LootEx` and the
four parallel mod models - this plan schedules nothing, and Phase 3 deleting that code is a
*staging* action reversible from the tag, not a decision that it is retired.

**Separate movement from behaviour.** Keep file moves, formatting, structural change and
behaviour change in different commits. During Phase 5 especially, a commit that both relocates
a module and changes what it does is very difficult to bisect against a live client.

## Known Unknowns

Recorded rather than guessed. These are in addition to the structural unknowns in
[dependency-map.md](../refactor-baseline/dependency-map.md#known-unknowns) and
[component-register.md](../refactor-baseline/component-register.md#known-unknowns), which all
still apply.

1. **Whether the live boot set matches the static boot closure.** Phase 1 resolves this. Until
   it does, the 272-module figure and the entire Phase 2 cut ranking are static claims.
2. **Whether the MVP gate should include the `Widgets/System` tier.** Excluding it is
   recommended above and is a judgement about sequencing, not a finding. Including it is
   defensible if multibox behaviour must be continuously exercised during Phases 2 to 4.
3. **Whether the facade cycle is load-bearing at runtime.** Carried unchanged from the
   baseline: `Py4GWCoreLib/__init__.py` has import-time side effects (`sys.path` mutation,
   native module import) and those may be *why* the pattern exists. Phase 2 repoints internal
   imports and Phase 4 finishes the job; neither may proceed on the assumption that the side
   effects are incidental. Establish this before any core split.
4. **What the deferred `frenkeyLib` severance costs in practice.** The six deferred edges break
   identify, salvage and auto-inventory when their functions run. How much of the MVP's useful
   behaviour that removes was not measured.
5. **Whether the offline harness is enough coverage to refactor 206k lines against.** It is 18
   files, of which Phase 0 executed all 18 at `refactor-origin`: **11 pass, 7 fail**. The 7
   failures are pre-existing and are diagnosed in
   [refactor-phase-0-waypoint.md](../records/refactor-phase-0-waypoint.md) - four were harness
   staleness, one pair is already slated for removal, and exactly one reported a live
   production defect. Phase 0 repaired the four and the production defect and deliberately
   left the condemned pair red, so the suite now stands at **16 pass, 2 fail** with both
   failures known. The offline harness being sufficient coverage for 206k lines remains
   unproven regardless; this is why every phase exit requires a live gate.
   This plan relies on the live gate at every phase precisely because the offline suite is not
   sufficient on its own.
